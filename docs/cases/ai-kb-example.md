# AI 知识库问答案例

> 当前状态：已完成基础版  
> 典型场景：内部文档问答、帮助中心、产品说明、操作手册查询

## 问题背景

团队资料常常散落在文档、FAQ、产品说明、知识库和聊天记录中。用户真正遇到的问题，不是“没有资料”，而是“找不到、看不完、找到了也不确定是不是最新的”。这类场景非常适合通过 RAG 做结构化问答。

## 目标

- 用自然语言快速找到相关知识
- 让回答尽量引用明确来源
- 降低用户在多份文档中来回跳转的成本

## 方案结构

```text
资料整理
  -> 文档切片
  -> 建立检索索引
  -> 用户提问
  -> 检索相关片段
  -> 模型生成答案并附来源
```

## 执行流程

### 1. 整理知识源

先明确哪些文档是真正可信的资料源，并建立更新机制。知识库问答的第一前提不是模型，而是资料治理。

### 2. 切片与索引

把文档拆成适合检索的片段，保留标题、章节、更新时间、来源链接等元信息，方便检索和引用。

### 3. 构造回答约束

提示模型只能基于提供材料回答，并在信息不足时明确说明，而不是自行补全。

### 4. 给出来源

答案最好附带引用片段、来源标题或原始文档链接，这样用户可以继续深挖，也更容易建立信任。

## 关键指标

| 指标         | 关注点                   |
| ------------ | ------------------------ |
| 检索命中率   | 能不能找到真正相关的资料 |
| 回答准确率   | 检索到后能否正确组织答案 |
| 来源可追溯性 | 用户能否快速确认出处     |
| 更新时效性   | 文档更新后能否及时生效   |

## 常见问题

- 文档切片不合理，导致关键上下文被拆散
- 资料重复或冲突，模型难以判断哪一条更可信
- 只看生成效果，不单独评估检索质量

## 局限与复盘

- 知识库质量差时，RAG 只能放大问题，不会自动修复问题
- 如果问题本身不依赖外部知识，RAG 反而会增加系统复杂度
- 真实项目里应把“资料更新机制”视为和模型同等重要的模块
