# RAG 检索增强生成

> 当前状态：已完成基础版  
> 适合读者：希望让 AI 基于企业知识、产品文档或私有资料回答问题的人

## 为什么会需要 RAG

单纯依赖模型自身记忆时，回答容易过时、失真，或无法覆盖企业内部知识。RAG 的目标不是让模型“更聪明”，而是让它在回答前先拿到更相关、更可信的上下文。

## RAG 的基本思路

RAG 通常分成两步：

1. 先从知识库里检索出相关内容
2. 再把这些内容作为上下文交给模型生成答案

这意味着系统的质量，不只取决于模型，也取决于资料质量、切片策略、检索策略和答案生成方式。

## 一个典型 RAG 流程

```text
用户提问
  -> 问题改写或意图识别
  -> 检索相关文档片段
  -> 对结果排序或过滤
  -> 组合上下文
  -> 模型生成答案
  -> 返回引用与答案
```

## 核心组成

### 1. 文档预处理

把原始资料切成适合检索的小块，并保留标题、来源、章节等元信息，便于后续定位和引用。

### 2. 检索阶段

根据问题找回最相关的文本片段。这个阶段决定模型有没有机会看到正确材料。

### 3. 生成阶段

模型基于检索结果输出答案。这里需要明确约束，例如“仅根据提供材料回答”“引用来源”“信息不足时明确说明”。

## 什么时候适合用 RAG

- 企业内部知识问答
- 产品文档、操作手册、FAQ 问答
- 需要基于最新资料回答的问题
- 需要让答案可追溯、可引用的场景

## 什么时候不一定需要 RAG

- 问题本身不依赖外部知识，只是通用改写、总结或生成
- 数据量很小，直接把资料作为上下文传给模型即可
- 需求更像工作流自动化，而不是知识查询

## 常见问题

### 检索不到，不是模型问题

如果切片太碎、太粗，或者元信息不足，即使模型再强也无法凭空补齐事实。

### 检索到了，但答案还是不对

这通常和上下文拼接方式、提示词限制、引用策略、排序质量有关，不一定是检索本身出了问题。

### 资料本身质量差

RAG 不会自动修复混乱、重复、过期或冲突的知识库。知识治理仍然重要。

## 实践建议

1. 先用少量高质量资料跑通流程，再扩数据规模。
2. 为答案附带来源，方便用户核验。
3. 分别评估“检索质量”和“回答质量”，不要混在一起看。
